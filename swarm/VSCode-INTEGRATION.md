# VS Code integration / migration
1. Use a disposable feature branch and approved sandbox. Copy the profiles and swarm directory after checking collisions. Select the Copilot harness (not deprecated Local) in VS Code. Open Chat: Open Customizations > Agents. Verify every profile is recognized. Only orchestrator is shown in picker by default; helpers can be invoked by name. Temporarily change user-invocable for manual fallback if necessary.
2. Confirm runtime tool inventory and model selection. Native Copilot delegation uses task (agent alias); older Local uses agent/runSubagent and different configuration. Do not add Local-only `agents` allowlist or `handoffs` to these profiles. Editor schema acceptance is not proof of permissions; inspect actual calls. `strict-tools-list` may not carry through all VS Code conversion paths. Check reviewer read/search only; use OS/repo boundaries, not prompt text, for protection. Stop if unexpected tools are present. Do not enable blanket terminal approval.
3. In a throwaway repo, ask orchestrator to invoke swarm-cpp-reviewer on a harmless file, return an evidence-backed finding, and not modify it. Check real subagent activity, then test two concurrent read-only reviewers. Test a forced escalation and resume in a new conversation. If native delegation unavailable, run manual roles and stay shadow-only.
4. Optional migration only: map the existing planner, contributor and QA. For a standalone pilot skip this mapping and use the shipped profiles as-is. Preserve useful instructions. For each, compare tools, role, inputs, outputs and stopping conditions to the corresponding starter. In particular, remove automatic contributor handoff from planner when driven by orchestrator, ensure contributor stops after one approved increment, and make QA independently review final candidate. Keep existing profiles untouched until team approves the migration. Then change explicit role names in orchestrator and launch prompt or rename approved copies; ensure subagents cannot self-delegate outside their assignment. Do not enable ADO/GitHub write tools for any role.
5. Optional read-only Azure DevOps MCP: use Microsoft-approved remote server configuration example under templates; merge manually into `.vscode/mcp.json` only after organizational approval. Replace organization placeholder. Authenticate via approved Entra account. Verify only read-only work-item tools; limit underlying user permissions as well. Intake in a separate approved session: retrieve story ID, revision, description, acceptance criteria, links as needed; save a sanitized snapshot under run folder, pass to planner as data. No MCP is necessary for initial pilot; paste story manually. No automatic ticket edits.
6. Use existing feature branch process, local candidate commits only when explicitly authorized, and manually open/update PR after final QA. Required CI checks and human approvals remain enforced by GitHub branch rules. Do not give swarm push, merge or deployment privileges. Run folder is local, ignored; share approved review digest in PR if team permits. Do not upload raw prompts, logs or source outside company policy.
7. Select a supported model via frontmatter completions after measuring reviewer performance; use an independent model family for test review where approved. No fixed model IDs shipped. Evaluate against your own reviews before switching modes.
